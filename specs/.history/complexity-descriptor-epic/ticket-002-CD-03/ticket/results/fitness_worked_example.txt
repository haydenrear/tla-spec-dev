CD-03 worked example: self-configured fitness functions over the complexity descriptor
======================================================================================

Recorded 2026-07-21 from a live run of the shipped toolchain
(python3 scripts/tla_spec_dev.py --spec-root specs analyze complexity ...).
Demo project: $DEMO = /private/tmp/claude-501/-Users-hayde-IdeaProjects-tla-spec-dev/542a318c-a17c-4cd4-be34-42732ff10463/scratchpad/fitness-demo

The story: the project's agent reads the descriptor of a small pipeline model,
decides the shape it should keep, writes TWO COMPOSED RULES that persist with
the project, and a LATER scan -- after someone adds a god-action -- surfaces
ONE FIRING so the future agent is notified. Advisory throughout: exit code 0
on every scan below.

--------------------------------------------------------------------------------
STEP 0 -- the project before any rules: Demo.tla (mode/jobs/done pipeline)
--------------------------------------------------------------------------------

    ---------------------------- MODULE Demo ----------------------------
    EXTENDS Naturals
    
    VARIABLES mode, jobs, done
    
    vars == << mode, jobs, done >>
    
    Init ==
      /\ mode = "idle"
      /\ jobs = 0
      /\ done = 0
    
    Start ==
      /\ mode = "idle"
      /\ mode' = "running"
      /\ UNCHANGED << jobs, done >>
    
    Enqueue ==
      /\ mode = "running"
      /\ jobs < 3
      /\ jobs' = jobs + 1
      /\ UNCHANGED << mode, done >>
    
    Complete ==
      /\ jobs > done
      /\ done' = done + 1
      /\ UNCHANGED << mode, jobs >>
    
    Archive ==
      /\ done > 0
      /\ done' = done - 1
      /\ UNCHANGED << mode, jobs >>
    
    Next == Start \/ Enqueue \/ Complete \/ Archive
    
    TypeInvariant ==
      /\ mode \in {"idle", "running"}
      /\ jobs \in 0..3
      /\ done \in 0..3
    
    Spec == Init /\ [][Next]_vars
    =============================================================================

--------------------------------------------------------------------------------
STEP 2 -- the project's agent adds two composed fitness functions
--------------------------------------------------------------------------------

The agent writes $DEMO/fitness_functions.json (persists with the project;
the .json form parses with the standard library alone, so it works under the
bare python3 this CLI is pinned to):

    {
      "fitness_functions": [
        {
          "name": "stay-decomposed",
          "description": "no god-state variable, and the busiest component stays at 4 actions or fewer",
          "rule": {
            "all": [
              {"fact": "god_state_count", "op": "==", "value": 0},
              {"fact": "max_component_actions", "op": "<=", "value": 4}
            ]
          }
        },
        {
          "name": "state-space-in-check",
          "description": "static bound stays small and the jobs queue domain stays tiny",
          "rule": {
            "all": [
              {"fact": "bound", "op": "<", "value": 1000},
              {"fact": "variable_domain", "var": "jobs", "op": "<=", "value": 4}
            ]
          }
        }
      ]
    }

--------------------------------------------------------------------------------
What this shows
--------------------------------------------------------------------------------

1. Composable: each rule is an all-of over descriptor facts
   (god_state_count == 0 AND max_component_actions <= 4; bound < 1000 AND
   variable_domain(jobs) <= 4); any/not are equally available.
2. Persistent per-project: the rules live in the project's own
   fitness_functions.json and were not passed on any command line.
3. Notification: the later scan reports 'FIRED: stay-decomposed' with the
   leaf-level trace naming the measured facts that drove it, while
   'state-space-in-check' still holds -- two composed rules, one firing.
4. Advisory: every scan above exited 0. Firings report, never block.

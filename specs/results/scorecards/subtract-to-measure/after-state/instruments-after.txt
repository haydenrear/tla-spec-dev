INSTRUMENTS THAT CANNOT BE SHOWN TO FAIL, with the reason
------------------------------------------------------------------------------
  produced-code-instrument
      BY CONSTRUCTION AND ON PURPOSE, and this is the one row where that is the
correct answer rather than a defect. It is a THERMOMETER: it reports, refuses
nothing, gates nothing, and exits 0 on a tree that does not exist, a file that
does not parse and a file that is not UTF-8. `EXIT_OK = 0` is the only exit
constant in the file and `tests/test_code_complexity.py` asserts that against
the AST, not against prose. 'I could not measure this' is a completeness fact
printed with the path and the reason. The blind-spot row demonstrates the
inability rather than asserting it.

  suite-verification
      A PREDICTION DISAGREEMENT CANNOT MAKE IT RED. `verify_suite` prints
`*** DISAGREES ***` for a wrong prediction and then does not append it to
`problems`, and the function says so in its own closing disclaimer. Only two
conditions reach `problems`: a missing anchor tree, and a control run that is
already red on the UNMUTATED tree. So the one thing the mode is named for is
the one thing it cannot report, and every `predicted_suite` annotation in the
catalogue is unchecked prose. Filed as FI-02-DF-01.

  port-swap-driver
      NOT ON ITS EXIT CODE. `main()` ends `return 0` with no branch above it, so a
run that finds every control violated on every instrument, and a run that finds
none, are indistinguishable to any caller that reads the status. It has
ALREADY happened: `examples/validation/ab/eval/results/fi01/swap-reference_ports.json`
records PA-M14 as `control_red` and that run exited 0. Its printed verdict CAN
go red and does; nothing that consumes an exit code can see it. Filed as
FI-02-DF-02.

  manifest-self-records-tripwire
      SM-03 REPLACED THE REASON THAT USED TO BE HERE, WHICH WAS FALSE.

It said the only way to show it red is to break a real manifest "and the
shipped trees are the subject of every other measurement in this epic".
`SM-GM-I4` refuted that: a shipped file broken in a THROWAWAY tree turns the
sibling tripwire red in 23 executed tests, and since this ticket `run_pytest`
stages, so breaking a shipped file no longer means touching the shipped tree.
Two of the four rows that carried this reason are now `demonstrated-can-fail`.

WHAT IS ACTUALLY LEFT, and it is smaller and duller than the old sentence. Its
assertions read all THREE manifest trees -- `program_model`, `current`,
`desired_program_model` -- and cross-check each manifest's prose counts against
the module beside it, so a staged tree has to carry three manifests and three
TLA+ modules kept mutually consistent. Constructible; not constructed at SM-03,
which spent its staging budget on the two rows above. This row is counted in
"cannot be shown to fail" and it is a SCOPE statement about this ticket, not a
property of the instrument. `SM-03-DF-03`.

  port-declaration-tripwire
      SM-03 REPLACED THE REASON THAT USED TO BE HERE, WHICH WAS FALSE.

It said "NOT WITHOUT BREAKING A SHIPPED FILE ... no root a fixture tree could be
handed". `SM-GM-I4` refuted that for this whole family and `spec-yaml-tripwire`
and `source-citation-tripwire` are now demonstrated by breaking a shipped file
in a STAGED tree, which is what `run_pytest` does since this ticket. The old
sentence was a fact about the harness.

THE REAL OBSTACLE, MEASURED RATHER THAN ASSERTED. Staging it and seeding a
degenerate `target: "**"` DOES produce the extra failure --
`test_no_declared_port_target_is_degenerate[program_model]` appears and nothing
else changes. But the staged tree is not green to begin with: the file imports
`run_generated_case_adapters` transitively through `scripts/`, and a tree small
enough to stage cannot satisfy that import, so three unrelated nodes are red
before the seed lands.

AND THAT IS A DEFECT IN THE RUNNER, NOT IN THIS ROW. `demonstrate.py` judges an
EXIT CODE, so red-on-red is indistinguishable from red-on-green and the
demonstration would report `ok` for the wrong reason. `run_gap_mutants.py`
solved exactly this one directory over -- it runs each detector on the pristine
tree first and compares FAILURE SETS, never exit codes, because a `git archive`
tree has nine pre-existing failures. The registry runner has no such baseline.
Filed as `SM-03-DF-01`; NOT fixed here, because a second structural change to
the runner inside the ticket that is counting what the runner reports is how a
measurement stops being one.

  test-graph-nodes
      NOT IN THIS ENVIRONMENT. Running them needs the Test Graph toolchain -- gradle,
a JVM and JBang -- which this checkout does not provision, so no demonstration
constructed here would be re-runnable by the next reader. Worth recording
anyway: `test_graph/sources/spec_workflow_force_failure.py` IS a demonstrated
failing input, shipped, deliberately, as a negative-control node whose whole
purpose is to prove the graph can go red at all. It is the only instrument in
this repository that shipped one before FI-01.

  ticket-state-agreement
      THE PROPERTY IS UNWATCHED, WHICH IS WHY IT IS IN THIS TABLE. After a clean
`start_ticket.py FI-02`, `specs/tickets/FI-02/ticket.yaml` carries
`"status": "active"` while `specs/desired_program_model/ticket_plan.yaml` still
says `status.active_ticket: null` -- and the file an agent reads first is the
one that is wrong. `ticket.yaml`'s `status` is written once by the scaffolder
and read by NOTHING: `spec_evolution.py` reads only `seed_manifest`, and
`tla_spec_dev.py:active_ticket_id()` reads only the plan. No test compares
them. An enumeration of instruments that omitted the ones that should exist and
do not would be flattering itself. PA-02-DF-02, open.

  generation-refusal
      NOT WITHOUT A STAGED MANIFEST TREE THIS TICKET DID NOT BUILD, and the honest
reason is narrower than that: the refusal shares `validate_manifest` with
`manifest-validator` above, which IS demonstrated, so what is undemonstrated is
only that `generate_python.py` propagates it. Registered as a gap rather than
counted as covered by its neighbour.

  docs-generation-refusal
      THE THIRD CONSUMER OF THE SAME PREDICATE, and the same gap: `validate_manifest`
is demonstrated at `manifest-validator`, this file's propagation of it is not.
Thirty-seven lines, no test file of its own.

  tlc-dump-case-generation
      NOT WITHOUT A TLC RUN. Every refusal path needs a real DOT dump to refuse
against, and producing one needs a JVM and TLC, which this checkout does not
provision -- the same environmental reason `test-graph-nodes` carries, and it
is worth naming that TWO rows now cite it. `tests/test_generate_cases_from_tlc_dump.py`
covers the parsing, not the refusal.

  scaffold-overwrite-refusal
      CONSTRUCTIBLE AND NOT CONSTRUCTED. Two clear refusal paths at :38 and :54 and
neither has a test asserting the refusal; `tests/test_scaffold_spec_views.py`
covers what it EMITS, not what it declines to. This is a gap in the tests, not
in the instrument, and saying so is more use than a row that implies otherwise.

  workflow-convergence
      OVERLAPS `close-promotion-preconditions`, WHICH IS DEMONSTRATED, and this file
is the other half of that path. Not demonstrated separately here, and the
overlap is stated so that the two are not read as independent coverage of the
same close.

  arm-swap-driver
      THE ROW `FI-06-DF-01` LED WITH. Shipped by FI-04 in the SAME directory and the
SAME reconcile as `divergence.py` -- which FI-04 registered by hand while
writing `FI-04-DF-04` about exactly this failure. Absent for two epics.

Undemonstrated because a run needs a generated corpus and a sealed catalogue,
which is the `port-swap-driver` situation one row over. Unlike that one, its
exit code DOES carry the control state, so it is not `demonstrated-cannot-fail`
and must not be recorded as such.

  onboarding-scaffold
      `tests/test_onboard_program_model.py` covers what it SCAFFOLDS. No node asserts
a refusal, so there is nothing here to cite; 1408 lines whose declining
behaviour is untested.


DEMONSTRATED BLIND SPOTS -- a genuine break each one does NOT report
------------------------------------------------------------------------------
  effect-oracle
      a process.spawn is UNOBSERVABLE whatever a port declares, so any effect a child process performs is outside this oracle by construction -- the kill test must run outside the sandbox for exactly this reason, and says so on every run
  tla-complexity-descriptor
      a model 432x over its own declared state-space bound and 5x over its per-component variable bound: WARNINGS, and exit 0. There is no input that makes this instrument refuse on complexity, deliberately (MF-036, and CD-01: a tool that picks the boundary makes every edge legal by construction).
  produced-code-instrument
      a tree with a file that does not parse, a path that is not there, and a module 12 branches deep in every method: exit 0, every time. Nothing you can put in front of this instrument makes it refuse.
  catalogue-integrity
      it makes a MEASUREMENT catalogue's obligations of a SUPPLEMENT catalogue, so probing one control on one arm prints sixteen complaints that are all true of the wrong file, and it refuses every per-arm catalogue including two sealed ones
  control-decision-driver
      IT CANNOT MEASURE A PORTED TREE AT ALL. Its purge is keyed on ARM_MODULE_PREFIXES = ('quota_ledger',), so on a ported tree `domain` and `journal_file` stay cached and every mutant seeded in them runs against unmutated code: 15 of 15 false SURVIVED, no error, looking exactly like a clean measurement.
  port-swap-driver
      a red control changes nothing about the exit code, shown against the shipped source
  divergence-reachability
      IT CANNOT SEE A DIVERGENCE IT WAS NOT GIVEN A COMPARABLE ROW FOR. The comparable
row is DECLARED per catalogue row (`wired_by_default`), not derived, so a
catalogue that declares the wrong one moves the divergence count and nothing
here objects. That is the same declaration-executability shape FI-01-DF-04
recorded against PORT_REGION, in the instrument FI-04 shipped, and the failure
direction is NOT the safe one: a mis-declared comparable row produces a WRONG
COUNT rather than a refusal.

  scorecard-audit
      OPEN and UNVERIFIED findings are printed and then not counted -- only VIOLATION increments the exit code, so a claim whose commit does not resolve, and a repair that declares neither verdicts_moved nor verdicts_unmeasurable, both leave a green audit
  blinding-sanitiser
      THE VERIFICATION IS VACUOUS AGAINST ITS OWN VOCABULARY. `This is ARM B, the hexagonal treatment arm. I was given the HEXAGONAL prompt by HP-02.` -- the exact sentence PA-06-DF-11 measured -- passes CLEAN, because the grep runs AFTER the substitutions and looks for very nearly the set they just removed. The instrument reports zero problems on the leak it was written to catch.
  thermometer-tripwire
      a consumer that reads a previously written complexity JSON and gates on it WITHOUT EVER NAMING THE INSTRUMENT is invisible -- and that is the route the one real reader in this repository takes, so the scan can never be relied on alone
  dispatch-record
      IT CANNOT SEE A DISPATCH THAT WAS NEVER RECORDED. An empty evidence directory
verifies GREEN. The checker's whole subject is the rows it was given, so an arm
dispatched with no row at all is invisible to it, and the exit code a reader
watches says nothing is wrong.

THE FAILURE DIRECTION IS NOT THE SAFE ONE, and this is not hypothetical: it is
the state ARMS A AND B ARE IN RIGHT NOW. Only arm C has a row, and that row is a
reconstruction. Arm B's sealed 105 unique content lines -- the denominator of the
entire length match -- is a number about the file on disk with no artifact
saying that is what arm B received. FI-05-DF-02, MAJOR, mine and open.

The verdict is not silent about it -- `verify` prints "NO DISPATCH RECORD" and
`check_catalogue.py --arms` without `--dispatch-dir` prints that every number
below it came from the bytes on disk -- but a PRINTED WARNING IS NOT A RED, and
counting it as one is how a control goes soft. Declared as an inability, per R2.

  prediction-seal
      IT CANNOT CHECK A PREDICTION THAT NAMES NO MUTANT AND NO COLUMN. A row
predicting "zero cells, on every row of the table" has no cell to look up, so it
is reported UNPARSED and THE EXIT CODE IS 0.

The failure direction is green-looking silence. In the only real file this has
ever been run against it reaches 1 of the 3 no-kill rows: N05 is checked, N03
and N07 are not, and a reader watching only the exit code would take a
one-problem report as covering all three. FI-05-DF-03, mine and open.

NOT REPAIRED BY WIDENING THE PARSER, deliberately. Expanding "every row of the
table" into a cell list would have the checker inventing the subject the sealer
declined to state, which is a worse failure than saying it cannot check. The
UNPARSED block exists so the gap is printed rather than assumed, and the row is
declared here as an inability per R2 rather than counted as coverage.

  enumeration-runner
      IT CANNOT SEE A SLOT THAT DEMONSTRATES NOTHING, ONLY ONE THAT DEMONSTRATES WRONGLY. `expect_passed` closes the vacuous-run hole SM-GM-I1 found, but a slot citing a node whose assertions are all trivially true still reports `ok` at full count -- the runner judges that the cited test PASSED, never what it asserted.
  registry-enumeration-coverage
      IT CANNOT SEE A REPO TRIPWIRE THAT IS A PYTEST FILE. The predicate is a `__main__` guard plus a nonzero exit path, and `tests/test_code_complexity.py` and its four siblings have neither -- so the five rows the registry most depends on are exactly the five this check would never have asked for.
  gap-mutant-runner
      IT DETECTED ITSELF. Its catalogue-integrity test reads mutant anchors out of whichever tree it runs in, which during a measurement is the MUTATED one, so it fired on every mutant and on two of them was the ONLY new failure -- scoring both DIES where the repository catches neither. Excluded from the verdict and reported per cell, not repaired.

Every declared demonstration reproduced.

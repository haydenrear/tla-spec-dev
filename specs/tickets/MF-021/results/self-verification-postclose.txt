The `tla-spec-dev` on PATH runs the INSTALLED skill copy, not the worktree.
Because this repository IS tla-spec-dev, every validation command routed through

under test. The pre-fix promotion therefore ran, unchanged, against the fixed
worktree.

Recovery: the close was fully reverted -- ticket workspace moved back out of the
history entry, the history entry deleted, `git checkout -- specs/current`, and
the promoted-in file removed. `git diff --quiet HEAD -- specs/current` confirmed
specs/current was byte-identical to pinned commit a37f662 before retrying.

------------------------------------------------------------------------------
FINDING FOR THE EPIC OWNER — not fixed here, out of MF-021's scope
------------------------------------------------------------------------------

Attempt 1 is a real defect independent of the one this ticket fixes: for this
repository, `tla-spec-dev` on PATH is not the code under test. Any ticket that
validates via the bare binary is validating the installed skill, and a fix to
promotion (or any other CLI behavior) will appear not to work -- or worse, will
appear to work while the shipped copy misbehaves.

This also means MF-012's and MF-020's losses would have recurred for every
future ticket until the installed skill is re-synced, even with this fix merged.

Recommended follow-up (owner decision, architectural):
  1. After merging, run `skill-manager sync` so the installed spec-double-compiler
     carries this fix -- otherwise the next ticket loses the file again.
  2. Consider having the epic's validation matrix invoke
     `python3 scripts/tla_spec_dev.py` rather than `tla-spec-dev` whenever the
     repository under test IS tla-spec-dev, so the CLI lifecycle graph and the
     close step exercise the branch rather than the installed copy.
